# 校招提示词验收样例

本文件是对 `.agents/prompts/` 的回归约束，不是候选人事实源。

## 案例 1：非纯技术岗位要进入宽投队列

**给定**：候选人有内容、项目协作与多 Agent 工作流经历；JD 为“用户运营”。

**期望**：即使没有直接用户运营实习，也必须为 `broad_apply` 或 `opportunistic_apply`，列出真实缺口；不得因为专业或 60 分以下而跳过。

## 案例 2：纯技术岗位缺证据时默认跳过

**给定**：同一候选人；JD 为“后端开发工程师”，要求 Java、数据库与服务端项目。

**期望**：若事实库无直接证据，结果为 `skip_default`，但保留用户强制投递入口；不得把 Prompt/Agent 项目转换为后端研发经验。

## 案例 3：AI 产品经理必须证据化

**给定**：JD 包含 Workflow、Prompt、LLM、RAG、SQL/Python；事实库仅明确多 Agent 工作流、提示词、需求规格、测试模板，以及 Android 半移植项目。

**期望**：

- 将需求、Prompt、工作流、规格和测试写为真实 AI 应用产品相关证据；
- 对 RAG、SQL/Python 数据分析或模型训练写“无直接证据/待补”，不放进技能栏；
- 可将 RAG、SQL/Python 等作为“岗位思考 / 产品方案”的检索和讨论对象，使用“提出/建议验证”等现在时，不得混入候选人的过往经历或声称已经上线、取得指标；
- 第二学位预计毕业时间必须是 2027/06；
- 每个简历要点都应能逐条指向经历库事实。

## 案例 4：核心项目不得被机械压短

**给定**：事实库中的核心项目同时包含项目目标、模块拆分、工具方法、交付物和验证结果。

**期望**：

- 先生成完整内容母版，再制作一页投递版；
- 核心项目默认保留 4–6 条不同维度的证据，至少覆盖问题/需求、方案或 Workflow、关键执行、评测验证、结果交付中的四类；
- 次要经历保留 1–2 条；
- 不得以“总 Bullet 不超过 10 条”或固定字符数为由，将事实充足的核心项目压成 1–2 条；
- 每条目标控制在 1–2 行，信息过多时拆条，不把全部过程塞入一个长复句。

## 案例 5：广投不等于简历乱塞经历

**给定**：目标为 AI 产品经理；事实库同时包含 AI Workflow、网申 Harness、用户调研、可安装的游戏模式移植 Demo、游戏 MOD、游戏评测和文学编辑经历。

**期望**：

- 岗位仍可按宽投规则进入候选池；
- 每条经历单独计算简历相关度分；
- 网申 Harness、多 Agent Workflow 和用户调研进入定制简历；
- 可安装的游戏模式移植 Demo 可作为 55–69 分支持经历，用于证明功能拆分、技术可行性和原型交付；必须保留其真实“游戏模式迁移”语境，不能包装成 AI 项目；
- 游戏 MOD、游戏评测和文学编辑因直接相关度不足或证据重复而剔除；
- JD 的 SQL、RAG、算法/后端协作若无事实证据，标为缺口，不得用“测试、内容质量、使用 AI”强行替代；
- 一级板块固定为教育经历、实习/工作经历、实践经历、自我能力。

## 检查方式

每次修改提示词或生成定制稿后，人工检查四项：广投规则、技术岗防误投、事实不越界、核心项目信息深度。任一失败，禁止生成最终 PDF 或批准清单。

对“岗位思考 / 产品方案”额外检查：它使用“针对该岗位提出 / 建议验证”等表达；不能写成已完成、已上线或已获得指标的过往成果。
