# Profile 数据说明

本目录保存候选人材料的唯一事实与投递偏好。后续任何简历定制、岗位分析或网申任务均应按以下顺序读取：

1. `01-candidate-profile.md`：**唯一已确认经历事实源**；只能改写、排序和取舍。
2. `preferences.md`：求职方向、材料结构和筛选偏好。
3. `application-answers.md`：网申可填写答案及敏感字段边界。
4. `drafts/`：导入审计与待确认候选事实；**不得直接用于简历或网申**。
5. `resume-exemplars/`：用户明确批准的私有模范简历快照；只作相似岗位的结构和判断参考，**不是事实源或选材批准**。
6. `resume-baselines/`：一次性审计后的私有成品执行基线；保存内容、源文件/事实库哈希、角色方向和复用状态，**仍不是事实源**。
7. `resume-claims.json`：通过事实校验且具有批准来源的完整简历表达；每条绑定 `fact_ids`、经历、角色族和游戏语境，供 `fast-assemble` 整条复用，**不是原子事实源**。

## 更新协议

- 新材料先进入 `drafts/`，每条记录标明来源、状态与待确认问题。
- 仅在候选人确认后，才将事实合并到 `01-candidate-profile.md`，并在该文件保留来源与确认日期。
- 发生冲突时以 `01-candidate-profile.md` 为准；不得根据旧简历、JD、参考简历或措辞推断新事实。
- 模范简历按角色族和 JD 关键词阈值匹配；每次仍须重新读取事实库、分析 JD、评分全部经历并取得人工批准。
- 成品基线仅在当前事实库哈希一致、状态为 `reusable`、角色族/方向一致且无需改变经历组合或核心故事时进入轻微调；否则重新审计或转完整重写。
- 扫描旧简历产生的事实候选先写入批量差异报告；只有 `review_queue` 中经用户确认的项目才可通过既有 `fact-diff` 流程合并。批准表达可以复用措辞，但不能把新数字或新职责自动升级为事实。
