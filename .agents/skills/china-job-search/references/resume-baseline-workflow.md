# 成品简历基线与轻微调工作流

## 边界

- `profile/01-candidate-profile.md` 仍是唯一事实源；基线只是一份已审计内容快照。
- 每次只处理一个完整 JD。公司招聘首页、岗位大类或公告标题不能替代职责和要求正文。
- 轻微调不改变经历组合、每段经历的核心故事和事实边界；需要上述改变时进入待批准重写批次。
- 轻微调的 HR 通过允许生成 HTML/PDF，但不批准岗位、附件上传或提交申请。

## 基线入库

运行 `scripts/resume_baseline.py audit`，扫描用户指定的成品目录及 `applications/`：

1. 对 PDF 文件和规范化文本分别计算 SHA-256，合并重复内容但保留全部来源路径。
2. 关联可编辑 HTML/Markdown、批准内容母版、岗位目录、HR 记录和视觉验收记录。
3. 对照当前联系方式和已知撤回事实执行确定性检查。
4. 将内容与元数据保存到受 Git 忽略的 `profile/resume-baselines/`。
5. 只有 `reusable` 可进入自动轻微调；其余状态分别表示需修复、仅供参考或禁止复用。

当事实库 SHA-256 或任一源文件 SHA-256 变化时，原索引只能报告 `full_rewrite`/重新审计，不能静默沿用。

## 具体岗位展开

- 仅纳入正式校招；跨城岗位保留。
- 暑期/日常实习、已过期岗位、纯硬技术岗位默认阻断。
- 公司招聘项目必须展开为职责和要求可读取的具体岗位；同一公司不同岗位分别成行。
- 以规范化具体投递 URL 为第一去重键，以“公司 + 具体岗位”为第二去重键。
- 已有成功回执的同一岗位不得再次生成或投递；公司级“已投递”记录不足以推断该公司的其他岗位已投。
- 登录、验证码、JS-only 页面或无法可靠读取的 JD 标记 `待读取JD`/`阻断`，不通过标题猜测。

## 路由和 HR 闸门

使用 `resume_baseline.py route` 选择路线：

- `light_tune`：角色族和方向完全一致，事实库哈希有效，所需经历已在基线中，且不存在选材或故事层变化。
- `full_rewrite`：无合格基线、跨角色族/方向、需新增或删除经历、需重做核心故事、基线含过期事实，或事实库哈希失效。

轻微调完成后，先运行确定性事实检查，再调用一次全新的只读 HR Reviewer。HR 输入必须包含完整 JD、当前事实、基线元数据、调整前后正文和差异。输出遵循 `light-tune-hr-review.schema.json`。

- `strong_push`、总分不低于 9.0、六维均不低于 8.0：可以进入制版。
- 纯措辞/顺序问题：最多两次局部修订，每次使用全新 HR Reviewer 复核。
- 选材、故事、事实冲突或第三个候选仍不合格：写入待重写批次；用户批准批次前不得启动双 Writer。
- 批次批准后转交 `$custom-resume`，完整保留选材/故事批准、双 Writer、融合、审计、HR 和最终内容批准。

## 制版和状态

轻微调 HR 通过后，使用 `resume` Skill 在 `applications/<公司>_<具体岗位>/resume/` 生成可编辑 HTML 和 PDF，并完成视觉、文本层与 ATS 检查。工作簿中的 `可投递` 仅表示材料已准备，不表示岗位或附件已获投递批准。
