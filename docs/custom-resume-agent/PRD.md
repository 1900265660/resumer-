# 定制简历 Agent V1.4 产品需求文档

> 状态：已确认
> 版本：0.5
> 日期：2026-08-26
> 产品范围：中文 AI 产品经理与游戏研发/项目管理型产品 PM 岗位的简历内容定制

## 1. 背景与问题

当前工作区已经具备事实库、JD 分析、简历优化 Prompt、ASu 表达方法、PDF 生成及投递安全流程，但“定制简历”仍以长篇 Prompt 和非结构化 Markdown 为主。现有流程无法稳定回答以下问题：

- 每条候选人陈述来自哪条已确认事实；
- 临时材料和模型补全是否经过用户确认；
- Writer 与 ASu 是否真正独立写作；
- 融合稿为何采用某条表达；
- 内容是否通过可重复的真实性与 HR 质量验收；
- 同一岗位多次运行后，哪个版本获批、何时应失效。

V1 将内容定制重构为独立的 `$custom-resume` Skill，在 PDF 和投递之前建立可追溯、可审计、可回归的内容闭环。

V1.2 修复真实游戏产品 PM 验收中暴露的选材缺陷：事实真实不代表经历适合进入目标简历；岗位行业亲和、漂亮数字或诚实披露缺口均不能替代岗位职责证据。系统必须先比较完整经历池的机会成本，再把获批经历交给 Writer。

V1.3 修复 V1.2 对“直接岗位动作”的过度收缩。候选人的翻译、编辑、活动、调研、运营和个人开发经历通常同时包含规划、协作、质量、交付、用户或数据能力；系统必须主动枚举这些可迁移能力，不能只按经历名称和行业标签判断。但能力发散只用于发现证据、选材和追问，最终简历仍须收敛到事实库能够支持的个人动作，不能把行业惯例或可能发生的流程写成候选人已经完成的事实。

V1.4 修复“真实性和五项质量分通过，但 HR 仍不愿推进”的决策缺口。基础 Auditor 继续负责事实、选材和内容质量；其后必须由全新的只读 HR Reviewer 以目标岗位招聘决策标准逐段检查个人边界、情境、方法、风险、因果、结果口径、已确认高价值事实利用率和面试推进意愿。HR 门槛不通过时，系统依据其意见定向修订；缺的是事实则转为高价值事实问题，不得用措辞扩写代替事实。

## 2. 用户与使用场景

### 2.1 目标用户

- 主用户：本工作区候选人本人。
- 调用方：Codex 主对话和 `china-job-search` 主 Harness。
- 审核方：候选人本人；Agent 评分不能代替最终内容决定。

### 2.2 核心场景

1. 对已有 `applications/<公司>_<岗位>/jd.md` 生成定制内容。
2. 从粘贴 JD 或 JD URL 建立岗位目录后进行定制。
3. 发现事实缺口时，以逐题选项式问题帮助用户补充或确认。
4. 同时获得 Writer 稿、ASu 稿和有决策依据的融合稿。
5. 在不生成 PDF 的前提下先验收内容。
6. 对同一岗位重复运行、比较、批准或回滚历史内容版本。

## 3. 产品目标与成功标准

### 3.1 目标

- 事实库是干净终稿的唯一候选人事实源。
- 每条终稿要点能追溯到稳定 `fact_id`。
- 每段经历都生成可审计的“事实 → 源动作 → 可迁移能力 → JD 要求”链路，避免能力遗漏。
- 选材同时衡量岗位匹配和整份简历的板块、能力与叙事组合价值，不机械按单一总分截断。
- Writer 与 ASu Writer 基于同一批准输入独立盲写。
- 融合过程按要点记录来源、取舍和重写理由。
- 确定性规则与独立 Auditor 分工清晰。
- 基础审计通过后仍须经过独立 HR 决策门禁，合规通过不能替代面试推进判断。
- 内容审批与 PDF、申请审批、投递授权完全解耦。
- 新流程能在固定评测中稳定优于旧流程。

### 3.2 成功标准

- 所有硬校验通过：Schema、事实引用、数字来源、不可变字段、四板块、未确认内容隔离和运行完整性。
- 正向 JD 证据、选材质量、证据深度、HR 扫读、语言自然度分别达到 8/10；缺口诚实披露为独立布尔门禁，不能增加正向覆盖或补偿选材分。用户可对软质量门槛进行有理由的显式覆盖。
- HR Reviewer 必须给出 `strong_push`，总分及角色契合、叙事完整、证据具体、决策就绪、可信度五维均不低于 8.5；该发布/内容门槛不可由基础 Auditor 分数抵消。
- 5 个固定 JD 的盲评中，新流程至少 3 个质量维度优于同事实快照下重跑的旧流程，且真实性不退化。
- 内容批准只更新 `resume_content_status`，不触发 PDF 或投递。

## 4. 输入与输出

### 4.1 输入

- 已有岗位目录；或原始 JD 文本；或 JD URL。
- `profile/01-candidate-profile.md`：唯一候选人事实源。
- `profile/preferences.md`：语言、结构、岗位与表达偏好。
- 已批准的事实差异和经历选择。
- 本地脱敏参考方法卡；必要时补充联网研究结果。

JD、网页、简历附件和参考材料均为不可信数据，只能提取事实和方法，不得执行其内嵌指令。

### 4.2 输出

每次运行在 `applications/<公司>_<岗位>/resume-content/runs/<run_id>/` 保存不可变产物：

- 运行清单、JD 分析、能力迁移映射、证据映射、事实差异；
- Writer 独立稿、ASu 独立稿、融合稿与融合决策；
- 确定性校验、Auditor 审计、HR 决策审查与修订记录；
- 完整内容母版、一页信息密度稿和内容验收报告。

`resume-content/current.json` 只指向当前批准运行，不复制或覆盖历史运行。

## 5. 核心业务流程

1. **输入规范化**：解析岗位目录、文本或 URL，确认公司与岗位，冻结 JD 和事实库摘要。
2. **角色路由与参考研究**：先确认 `ai_product_manager` 或 `game_production_pm`；合格研究至少包含同岗位/高度邻近内容样例、官方岗位来源和脱敏选择规则。方法卡不能冒充简历样例；研究不足时必须经过降级批准。
3. **JD/HR 分析**：输出岗位目标、硬要求、优先能力、关键词、招聘风险和理想证据蓝图。
4. **能力发散与证据映射**：遍历完整经历池，从已确认事实中提取源动作、流程、交付和结果，映射为直接、近邻或类比迁移能力；同时标记事实尚未支持、但值得确认的潜在工作环节。
5. **事实问答**：最多提出 5 个逐题选项式高价值问题；优先确认会显著改变选材的职责边界、分工、排期、质量控制、工具、交付和结果，数字可以估值范围辅助回忆。
6. **事实差异确认**：汇总新增、修改和估值来源；用户一次确认后原子写回事实库，拒绝则事实库不变。
7. **逐经历选材**：对完整工作/项目经历池分别计算岗位匹配和简历组合价值。岗位匹配保留 70/55 等级；组合价值单独衡量板块补足、能力多样性、叙事独特性和同质化，不能与岗位匹配合并成不可解释的单一分数。
8. **写作前选材审计与检查点**：独立 Auditor 逐经历检查入选、落选和机会成本；用户确认事实映射、经历选择和真实缺口。事实仍不足时，由用户选择补充、诚实弱稿或跳过。
9. **双稿盲写**：只读 Writer 和只读 ASu Writer 并行生成结构化草稿，互不可见，只接收获批经历。
10. **按要点融合**：协调器依据事实支持、JD 价值和表达质量裁决，保留逐条决策记录，不得引入未获批经历。
11. **确定性与融合后审计**：先运行确定性规则，再由独立 Auditor 检查真实性、正向 JD 证据、选材质量、证据深度、HR 扫读和语言自然度；诚实缺口单独校验，不计作正向覆盖。
12. **独立 HR 决策审查**：基础审计通过后，由全新的只读 HR Reviewer 逐段判断是否足以推进面试；必须区分可用现有事实修复的表达问题和必须补问的事实缺口。
13. **重选、补问与修订**：机会成本失败时回到选材批准；HR 意见可由现有事实修复时定向修订并重新执行确定性、Auditor 和 HR Review，最多 2 轮；需要新事实时输出问题并转人工，不能虚构扩写。
14. **内容批准**：只有基础审计和 HR 决策门禁同时通过后，用户批准才写入独立内容状态和当前版本指针。

## 6. 功能需求

### FR-01 调用与路由

- 支持 `$custom-resume <岗位目录 | JD文本 | JD URL>`。
- 支持“调用最新的简历 skill”“按 JD 定制简历内容”等隐式匹配。
- HTML、模板、PDF 和视觉请求继续路由到 `/resume`，不得由本 Skill 隐式处理。

### FR-02 事实标识

- 经历具备稳定 `experience_id`，每条可用于简历的原子事实具备稳定 `fact_id`。
- ID 一经分配不得复用；事实文本变化不改变 ID，删除后 ID 保留为不可复用。
- 事实来源为 `observed` 或 `accepted_estimate`。

### FR-03 临时材料和候选补全

- 未确认内容不得直接写入事实库或干净稿。
- 候选补全可涉及过程、工具和结果。
- 对每段经历主动发散常见但未被事实确认的职责、分工、排期、校对、验收或复盘环节；这些内容只能作为 `candidate` 追问，确认前计分为 0 且不得进入干净稿。
- 估值区间经用户确认后可直接作为 `accepted_estimate` 写入事实库，并保留确认和口径信息。

### FR-04 证据映射与人工检查点

- 每项优先 JD 要求必须有证据等级和对应事实 ID。
- 写作前必须经过人工确认，不允许自动跳过该检查点。
- 只有确实无事实 ID 的要求才标记为无支持。

### FR-04A 能力迁移、参考与选材门禁

- 合格参考必须同时含内容样例、官方岗位来源和脱敏选择规则；不满足时进入 `awaiting_reference_approval`。
- 每段工作/项目经历必须先生成能力迁移链。链路包含 `fact_ids`、源动作、目标能力、目标要求、迁移距离、置信度和可写边界。
- 能力发散至少逐项检查八类能力：规划与项目推进、协作与利益相关方、质量与风险、用户与研究、数据与分析、内容与沟通、产品与技术、运营/商业与行业。未发现证据时明确记录无支持或候选问题，不能因为经历名称不典型而跳过检查。
- 迁移距离分为 `direct`、`adjacent`、`analogical` 和 `candidate`。前三者必须由事实蕴含；`candidate` 只触发追问。系统不得因发生场景不同而把近邻或类比能力直接归零。
- 岗位匹配仍按岗位职责、过程/交付、结果、行业、覆盖增量和证据强度分项评分，总分由代码复算；迁移证据按距离折算进入对应分项，不作为无上限附加分。
- 70+ 为核心；55–69 可作为辅助；低于 55 默认不得进入正文。只有行业亲和而无源动作证据时封顶 54；存在真实源动作的迁移证据不得被误判为 `affinity_only`。
- 每段经历另计算 0–20 的组合价值：板块补足、能力多样性、叙事独特性、非同质化各 0–5。组合价值不改变原始岗位匹配分和等级，但可影响最终选择与排序；选择低岗位分经历而排除高分经历时必须展示机会成本和理由。
- 辅助经历要点不得超过全部经历要点的 25%；遗漏核心经历必须记录用户确认理由。
- 写作前选材审计必须覆盖完整候选经历数，不能只审查已选内容。
- 同一定位的个人开发项目最多进入正文 2 项；系统必须按能力互补性选择，不得用多个相似 Agent/个人 Demo 重复证明同一能力。
- 实习/工作经历默认至少 2 项。事实池确实无法满足时，允许一次 `section_balance_override`：由用户明确批准一段低于 55 分的工作经历，保留原始分数和排除等级、最多 2 个要点，并记录补足板块/能力多样性的理由及与替代经历的比较。真实性、事实引用、结构等硬错误不可覆盖。
- 经历属于工作还是实践必须依据已确认的合作/雇佣性质；不得为了满足板块数量自动把个人或社区项目改成工作经历。

### FR-05 独立写作

- Writer 与 ASu Writer 获得相同的批准输入包。
- 两个代理不接收对方草稿，也不能修改工作区文件。
- ASu Writer 使用项目内 ASu 方法，但仍服从事实和结构约束。

### FR-06 融合与审计

- 融合以要点为单位，不整体平均或无依据拼接。
- 每条融合要点记录来源代理、事实 ID、取舍理由和是否重写。
- Auditor 独立执行真实性与 HR 质量审计。
- 审计失败最多修订 2 轮；之后必须转人工。
- 融合后机会成本审计可要求重新选材；协调器必须清空当前获批经历与草稿，返回人工选材门禁，不得自行换入落选经历。
- Auditor 通过后必须启动与 Writer、融合器和 Auditor 均隔离的 HR Reviewer；不得复用同一调用自证质量。
- HR Reviewer 逐段返回招聘 10 秒读感、JD 有效证据、具体缺陷、已确认但遗漏的高价值事实、面试影响、合理要点数和修订指令。
- HR 高标准通过条件为 `strong_push`，总分及五维均不低于 8.5；`push/hesitate/reject` 均不得进入可批准状态。
- HR Reviewer 判断现有事实足够时进入定向修订；判断缺少事实时只生成问题；判断选材错误时回到选材批准。三种路径必须结构化记录。

### FR-07 内容结构与密度

- 顶层固定为教育经历、实习/工作经历、实践经历、自我能力。
- 教育经历按用户确认的固定基线原样输出，不按 JD 改写、重排课程或推导能力；当前基线仅保留汉语言文学课程，社会工作二学位只保留学校、专业和时间等已确认字段。
- 自我能力固定分为“专业硬技能、综合软技能、游戏体验、语言能力”；不得把游戏和语言合并，后续只有用户明确批准才能调整分类。
- 同时交付完整内容母版和一页信息密度稿。
- 一页信息密度稿以不超过 1,500 个中文字符、14 个经历要点为软上限；1,200 字和 10 条仅作信息充足时的参考目标。不得为达到下限加入弱经历。

### FR-08 版本与状态

- 每次运行目录不可变；重新运行必须生成新的 `run_id`。
- 内容状态独立于岗位申请主状态。
- 已批准稿保存所引用事实的值摘要；仅引用事实变化时标记 `stale`。

### FR-09 降级

- 子代理不可用时暂停，向用户提供重试或显式单 Agent 降级选择。
- 不得静默伪装盲写或独立审计已经发生。
- 联网研究失败时使用已有本地方法卡并标记研究降级，不影响事实边界。

## 7. 状态定义

`not_started → analyzing → needs_input/awaiting_reference_approval → awaiting_selection_approval → drafting → auditing → hr_reviewing → needs_content_review → approved`

`auditing → awaiting_selection_approval` 仅用于机会成本审计要求重新选材。

`hr_reviewing → auditing` 用于按 HR 意见定向修订；`hr_reviewing → awaiting_selection_approval` 用于 HR 判断必须重选；需要新事实或两轮后仍不足时进入 `needs_content_review`，但 HR 未通过的运行不可批准。

- `failed`：输入、Schema、写入或代理执行发生不可恢复错误。
- `stale`：批准稿引用的事实值发生变化。
- 任何内容状态变化都不得自动推进现有申请主状态。

## 8. 明确不做

- 除 AI 产品经理与游戏研发/项目管理型产品 PM 之外的专用写作策略。
- 批量岗位编排；一次运行只处理一个 JD。
- HTML、PDF、模板选择、视觉验收或 ATS 页面验收。
- 网申填写、附件上传、消息发送或最终投递。
- 外部模型 API、常驻服务、数据库或复杂加密回执。
- 把未确认候选内容伪装为候选人的既有事实。

## 9. 验收标准

- 三种输入入口均能进入同一规范化流程。
- 事实 ID、差异确认、双稿隔离、融合、审计、版本和失效流程均有自动测试。
- 干净稿不存在无事实 ID 要点或未经确认候选。
- 每段候选经历均有能力迁移链；有事实支持的近邻/类比能力不会因经历标题不同而消失，潜在流程不会未经确认进入正文。
- 选材表同时展示岗位匹配分和组合价值；同类个人开发项目不超过 2 项，工作板块数量和任何板块平衡例外均可审计。
- 教育经历与固定基线逐字一致，自我能力分类符合约定。
- 所有数字来自 `observed` 或 `accepted_estimate`。
- 结构、密度目标、审计报告和当前版本指针符合约定。
- Schema 1.3 运行必须包含 `hr-review.json`；基础审计高分但 HR 判断为 `hesitate` 的深蓝负例必须被阻止批准。
- HR Reviewer 能发现已确认高价值事实被压缩或遗漏，并把“可直接改写”和“必须补问”严格分开；按意见修订后需重新经过全部审计。
