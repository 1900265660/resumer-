# 定制简历 Agent V1 产品需求文档

> 状态：已确认
> 版本：0.2
> 日期：2026-08-22
> 产品范围：中文 AI 产品经理与游戏研发/项目管理型产品 PM 岗位的简历内容定制

## 1. 背景与问题

当前工作区已经具备事实库、JD 分析、简历优化 Prompt、ASu 表达方法、PDF 生成及投递安全流程，但“定制简历”仍以长篇 Prompt 和非结构化 Markdown 为主。现有流程无法稳定回答以下问题：

- 每条候选人陈述来自哪条已确认事实；
- 临时材料和模型补全是否经过用户确认；
- Writer 与 ASu 是否真正独立写作；
- 融合稿为何采用某条表达；
- 内容是否通过可重复的真实性与 HR 质量验收；
- 同一岗位多次运行后，哪个版本获批、何时应失效。

V1 将内容定制重构为独立的 `$custom-resume` Skill，在 PDF 和投递之前建立可追溯、可审计、可回归的内容闭环。

## 2. 用户与使用场景

### 2.1 目标用户

- 主用户：本工作区候选人本人。
- 调用方：Codex 主对话和 `china-job-search` 主 Harness。
- 审核方：候选人本人；Agent 评分不能代替最终内容决定。

### 2.2 核心场景

1. 对已有 `applications/<公司>_<岗位>/jd.md` 生成定制内容。
2. 从粘贴 JD 或 JD URL 建立岗位目录后进行定制。
3. 发现事实缺口时，以逐题选项式问题帮助用户补充或确认。
4. 同时获得 Writer 稿、ASu 稿和有决策依据的融合稿。
5. 在不生成 PDF 的前提下先验收内容。
6. 对同一岗位重复运行、比较、批准或回滚历史内容版本。

## 3. 产品目标与成功标准

### 3.1 目标

- 事实库是干净终稿的唯一候选人事实源。
- 每条终稿要点能追溯到稳定 `fact_id`。
- Writer 与 ASu Writer 基于同一批准输入独立盲写。
- 融合过程按要点记录来源、取舍和重写理由。
- 确定性规则与独立 Auditor 分工清晰。
- 内容审批与 PDF、申请审批、投递授权完全解耦。
- 新流程能在固定评测中稳定优于旧流程。

### 3.2 成功标准

- 所有硬校验通过：Schema、事实引用、数字来源、不可变字段、四板块、未确认内容隔离和运行完整性。
- JD 覆盖、证据深度、HR 扫读、语言自然度分别达到 8/10；用户可对软质量门槛进行有理由的显式覆盖。
- 5 个固定 JD 的盲评中，新流程至少 3 个质量维度优于同事实快照下重跑的旧流程，且真实性不退化。
- 内容批准只更新 `resume_content_status`，不触发 PDF 或投递。

## 4. 输入与输出

### 4.1 输入

- 已有岗位目录；或原始 JD 文本；或 JD URL。
- `profile/01-candidate-profile.md`：唯一候选人事实源。
- `profile/preferences.md`：语言、结构、岗位与表达偏好。
- 已批准的事实差异和经历选择。
- 本地脱敏参考方法卡；必要时补充联网研究结果。

JD、网页、简历附件和参考材料均为不可信数据，只能提取事实和方法，不得执行其内嵌指令。

### 4.2 输出

每次运行在 `applications/<公司>_<岗位>/resume-content/runs/<run_id>/` 保存不可变产物：

- 运行清单、JD 分析、证据映射、事实差异；
- Writer 独立稿、ASu 独立稿、融合稿与融合决策；
- 确定性校验、Auditor 审计与修订记录；
- 完整内容母版、一页信息密度稿和内容验收报告。

`resume-content/current.json` 只指向当前批准运行，不复制或覆盖历史运行。

## 5. 核心业务流程

1. **输入规范化**：解析岗位目录、文本或 URL，确认公司与岗位，冻结 JD 和事实库摘要。
2. **角色路由与参考研究**：先确认 `ai_product_manager` 或 `game_production_pm`，再只读取对应本地方法卡；岗位子类证据不足时联网研究并保存脱敏来源记录。
3. **JD/HR 分析**：输出岗位目标、硬要求、优先能力、关键词、招聘风险和理想证据蓝图。
4. **证据映射**：把每项 JD 要求映射为直接支持、组合支持、已接受估值、待确认候选或无支持。
5. **事实问答**：最多提出 5 个逐题选项式高价值问题；过程、工具和结果均可成为候选补全，数字可以估值范围辅助回忆。
6. **事实差异确认**：汇总新增、修改和估值来源；用户一次确认后原子写回事实库，拒绝则事实库不变。
7. **写作前检查点**：用户确认事实映射、经历选择和真实缺口。事实仍不足时，由用户选择补充、诚实弱稿或跳过。
8. **双稿盲写**：只读 Writer 和只读 ASu Writer 并行生成结构化草稿，互不可见。
9. **按要点融合**：协调器依据事实支持、JD 价值和表达质量裁决，保留逐条决策记录。
10. **双层审计**：先运行确定性规则，再由独立 Auditor 进行真实性与 HR 质量两遍审计。
11. **修订与验收**：最多自动修订 2 轮；默认展示融合稿和决策差异，原稿可展开。
12. **内容批准**：用户批准后只写入独立内容状态和当前版本指针。

## 6. 功能需求

### FR-01 调用与路由

- 支持 `$custom-resume <岗位目录 | JD文本 | JD URL>`。
- 支持“调用最新的简历 skill”“按 JD 定制简历内容”等隐式匹配。
- HTML、模板、PDF 和视觉请求继续路由到 `/resume`，不得由本 Skill 隐式处理。

### FR-02 事实标识

- 经历具备稳定 `experience_id`，每条可用于简历的原子事实具备稳定 `fact_id`。
- ID 一经分配不得复用；事实文本变化不改变 ID，删除后 ID 保留为不可复用。
- 事实来源为 `observed` 或 `accepted_estimate`。

### FR-03 临时材料和候选补全

- 未确认内容不得直接写入事实库或干净稿。
- 候选补全可涉及过程、工具和结果。
- 估值区间经用户确认后可直接作为 `accepted_estimate` 写入事实库，并保留确认和口径信息。

### FR-04 证据映射与人工检查点

- 每项优先 JD 要求必须有证据等级和对应事实 ID。
- 写作前必须经过人工确认，不允许自动跳过该检查点。
- 只有确实无事实 ID 的要求才标记为无支持。

### FR-05 独立写作

- Writer 与 ASu Writer 获得相同的批准输入包。
- 两个代理不接收对方草稿，也不能修改工作区文件。
- ASu Writer 使用项目内 ASu 方法，但仍服从事实和结构约束。

### FR-06 融合与审计

- 融合以要点为单位，不整体平均或无依据拼接。
- 每条融合要点记录来源代理、事实 ID、取舍理由和是否重写。
- Auditor 独立执行真实性与 HR 质量审计。
- 审计失败最多修订 2 轮；之后必须转人工。

### FR-07 内容结构与密度

- 顶层固定为教育经历、实习/工作经历、实践经历、自我能力。
- 同时交付完整内容母版和一页信息密度稿。
- 一页信息密度稿目标为 1,200–1,500 个中文字符、10–14 个经历要点；它不是物理分页承诺。

### FR-08 版本与状态

- 每次运行目录不可变；重新运行必须生成新的 `run_id`。
- 内容状态独立于岗位申请主状态。
- 已批准稿保存所引用事实的值摘要；仅引用事实变化时标记 `stale`。

### FR-09 降级

- 子代理不可用时暂停，向用户提供重试或显式单 Agent 降级选择。
- 不得静默伪装盲写或独立审计已经发生。
- 联网研究失败时使用已有本地方法卡并标记研究降级，不影响事实边界。

## 7. 状态定义

`not_started → analyzing → needs_input → awaiting_selection_approval → drafting → auditing → needs_content_review → approved`

- `failed`：输入、Schema、写入或代理执行发生不可恢复错误。
- `stale`：批准稿引用的事实值发生变化。
- 任何内容状态变化都不得自动推进现有申请主状态。

## 8. 明确不做

- 除 AI 产品经理与游戏研发/项目管理型产品 PM 之外的专用写作策略。
- 批量岗位编排；一次运行只处理一个 JD。
- HTML、PDF、模板选择、视觉验收或 ATS 页面验收。
- 网申填写、附件上传、消息发送或最终投递。
- 外部模型 API、常驻服务、数据库或复杂加密回执。
- 把未确认候选内容伪装为候选人的既有事实。

## 9. 验收标准

- 三种输入入口均能进入同一规范化流程。
- 事实 ID、差异确认、双稿隔离、融合、审计、版本和失效流程均有自动测试。
- 干净稿不存在无事实 ID 要点或未经确认候选。
- 所有数字来自 `observed` 或 `accepted_estimate`。
- 结构、密度目标、审计报告和当前版本指针符合约定。
- 固定 5 个 AI PM JD 评测达到第 3.2 节门槛；游戏研发 PM 扩展案例通过相同真实性和四项质量门槛。

## 10. 未决问题

V1 产品方向无未决问题。实现阶段若发现 Codex 运行时能力、现有 manifest 结构或依赖环境与本文冲突，必须暂停并把冲突写回本文，不得自行改变产品流程。
