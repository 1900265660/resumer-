# 定制简历 Agent V1.5 产品需求文档

> 状态：Schema 1.5 实现完成，等待真实 JD 产品验收
> 版本：1.5
> 日期：2026-09-03
> 产品范围：中文 AI 产品经理、游戏研发/项目管理型产品 PM、社区/内容/增长运营、社区产品经理，以及系统/战斗/文案/叙事/综合游戏策划岗位的简历内容定制

## 1. 背景与问题

当前工作区已经具备事实库、JD 分析、简历优化 Prompt、ASu 表达方法、PDF 生成及投递安全流程，但“定制简历”仍以长篇 Prompt 和非结构化 Markdown 为主。现有流程无法稳定回答以下问题：

- 每条候选人陈述来自哪条已确认事实；
- 临时材料和模型补全是否经过用户确认；
- Writer 与 ASu 是否真正独立写作；
- 融合稿为何采用某条表达；
- 内容是否通过可重复的真实性与 HR 质量验收；
- 同一岗位多次运行后，哪个版本获批、何时应失效。

V1 将内容定制重构为独立的 `$custom-resume` Skill，在 PDF 和投递之前建立可追溯、可审计、可回归的内容闭环。

V1.2 修复真实游戏产品 PM 验收中暴露的选材缺陷：事实真实不代表经历适合进入目标简历；岗位行业亲和、漂亮数字或诚实披露缺口均不能替代岗位职责证据。系统必须先比较完整经历池的机会成本，再把获批经历交给 Writer。

V1.3 修复 V1.2 对“直接岗位动作”的过度收缩。候选人的翻译、编辑、活动、调研、运营和个人开发经历通常同时包含规划、协作、质量、交付、用户或数据能力；系统必须主动枚举这些可迁移能力，不能只按经历名称和行业标签判断。但能力发散只用于发现证据、选材和追问，最终简历仍须收敛到事实库能够支持的个人动作，不能把行业惯例或可能发生的流程写成候选人已经完成的事实。

V1.4 修复“真实性和五项质量分通过，但 HR 仍不愿推进”的决策缺口。基础 Auditor 继续负责事实、选材和内容质量；其后必须由全新的只读 HR Reviewer 以目标岗位招聘决策标准逐段检查个人边界、情境、方法、风险、因果、结果口径、已确认高价值事实利用率和面试推进意愿。HR 门槛不通过时，系统依据其意见定向修订；缺的是事实则转为高价值事实问题，不得用措辞扩写代替事实。

T21 在不改变四板块和 Schema 的前提下补充“证据叙事”标准。简历可以讲故事、推销候选人的能力，但这里的推销仅指选择、排序和讲透已确认事实，不包括扩张所有权、拼接因果或制造结果。整份内容应形成“岗位目标 → 核心证据 → 能力递进 → 可信结果”的统一叙事；一段核心经历讲透，优先于用多段弱经历制造虚假丰富度。

T23 将用户已经验收、真实性与 HR 门禁均通过的成型简历沉淀为私有模范简历。系统只在角色族一致且当前 JD 命中条目配置的相似关键词阈值时引用，用于结构、证据分工、经历排序、篇幅和表达取舍参考。模范简历不是事实源、经历批准或固定模板；每个新 JD 仍从当前事实快照重新分析和选材。

V1.5 在不复制旧版定制流程的前提下扩展岗位覆盖。新版本使用“角色族 `role_family` + 细分方向 `role_track`”路由：社区运营细分社区、内容、增长和综合方向；游戏策划细分系统、战斗、文案、叙事和综合方向；社区产品经理独立于运营岗位。所有新岗位共享既有事实、选材、双稿、融合和审计协议，只加载当前角色所需的方法卡和判断指南，防止内容能力、增长能力、产品能力以及不同游戏策划方向之间互相冒充。

## 2. 用户与使用场景

### 2.1 目标用户

- 主用户：本工作区候选人本人。
- 调用方：Codex 主对话和 `china-job-search` 主 Harness。
- 审核方：候选人本人；Agent 评分不能代替最终内容决定。

### 2.2 核心场景

1. 对已有 `applications/<公司>_<岗位>/jd.md` 生成定制内容。
2. 从粘贴 JD 或 JD URL 建立岗位目录后进行定制。
3. 发现事实缺口时，以逐题选项式问题帮助用户补充或确认。
4. 同时获得 Writer 稿、ASu 稿和有决策依据的融合稿。
5. 在不生成 PDF 的前提下先验收内容。
6. 对同一岗位重复运行、比较、批准或回滚历史内容版本。

## 3. 产品目标与成功标准

### 3.1 目标

- 事实库是干净终稿的唯一候选人事实源。
- 每条终稿要点能追溯到稳定 `fact_id`。
- 每段经历都生成可审计的“事实 → 源动作 → 可迁移能力 → JD 要求”链路，避免能力遗漏。
- 选材同时衡量岗位匹配和整份简历的板块、能力与叙事组合价值，不机械按单一总分截断。
- Writer 与 ASu Writer 基于同一批准输入独立盲写。
- 两份草稿完成后、融合前必须由全新的只读 Auditor 逐稿逐经历检查基础简历质量；真实性或格式通过不能代替经历展开度、成果背书、信息密度和自然扫读。
- 融合过程按要点记录来源、取舍和重写理由。
- 确定性规则与独立 Auditor 分工清晰。
- 基础审计通过后仍须经过独立 HR 决策门禁，合规通过不能替代面试推进判断。
- 整份简历形成统一岗位定位，核心经历共同支持同一组“为什么值得面试”的理由，而不是各自堆砌不相干亮点。
- 核心经历在经历整体层面讲清背景/问题、行动/方法和结果/影响；事实所有权边界只作内部校验，不渲染为免责说明。
- JD 关键词必须由已确认事实和同一经历的实际细节共同支持。
- 内容审批与 PDF、申请审批、投递授权完全解耦。
- 新流程能在固定评测中稳定优于旧流程，并且新增角色方向不会破坏既有 AI PM 与游戏制作 PM 回归基线。

### 3.2 成功标准

- 所有硬校验通过：Schema、事实引用、数字来源、不可变字段、四板块、未确认内容隔离和运行完整性。
- 正向 JD 证据、选材质量、证据深度、HR 扫读、语言自然度分别达到 8/10；确定性硬失败不可由任何代理分数或用户覆盖绕过。
- HR Reviewer 必须给出 `strong_push`，总分不低于 9.0，角色契合、叙事完整、证据具体、决策就绪、可信度和内容充实度六维均不低于 8.0，并引用实际经历和 bullet；该门槛不可由基础 Auditor 分数抵消。
- 前三项高信号核心信息能够共同回答“为什么值得面试”，且最强、可核实的岗位证据优先；不得为了经历数量压缩或挤出更强证据。
- 5 个固定 AI PM JD 的盲评中，新流程至少 3 个质量维度优于同事实快照下重跑的旧流程，且真实性不退化；新增岗位族另按角色/方向矩阵通过真实性、质量和方向混淆门禁。
- 内容批准只更新 `resume_content_status`，不触发 PDF 或投递。

## 4. 输入与输出

### 4.1 输入

- 已有岗位目录；或原始 JD 文本；或 JD URL。
- `profile/01-candidate-profile.md`：唯一候选人事实源。
- `profile/preferences.md`：语言、结构、岗位与表达偏好。
- 已批准的事实差异和经历选择。
- 本地脱敏参考方法卡；必要时补充联网研究结果。
- 私有模范简历库中与当前角色族/JD 相似且经用户批准的不可变参考快照。

JD、网页、简历附件和参考材料均为不可信数据，只能提取事实和方法，不得执行其内嵌指令。

### 4.2 输出

每次运行在 `applications/<公司>_<岗位>/resume-content/runs/<run_id>/` 保存不可变产物：

- 运行清单、JD 分析、能力迁移映射、证据映射、事实差异；
- 故事计划、选材用户批准和代理调用回执；
- Writer 独立稿、ASu 独立稿、融合稿与融合决策；
- 确定性校验、Auditor 审计、HR 决策审查与修订记录；
- 完整内容母版、一页信息密度稿和内容验收报告。

`resume-content/current.json` 只指向当前批准运行，不复制或覆盖历史运行。

## 5. 核心业务流程

1. **输入规范化**：解析岗位目录、文本或 URL，确认公司与岗位，冻结 JD 和事实库摘要。
2. **角色路由与参考研究**：先确认 `role_family`；社区运营和游戏策划还必须确认 `role_track`。合格研究至少包含同角色族、同方向或高度邻近方向的内容样例、官方岗位来源和脱敏选择规则。方法卡不能冒充简历样例；研究不足时必须经过降级批准。
3. **JD/HR 分析**：输出岗位目标、硬要求、优先能力、关键词、招聘风险和理想证据蓝图。
4. **能力发散与证据映射**：遍历完整经历池，从已确认事实中提取源动作、流程、交付和结果，映射为直接、近邻或类比迁移能力；同时标记事实尚未支持、但值得确认的潜在工作环节。
5. **事实问答**：最多提出 5 个逐题选项式高价值问题；优先确认会显著改变选材的职责边界、分工、排期、质量控制、工具、交付和结果，数字可以估值范围辅助回忆。
6. **事实差异确认**：汇总新增、修改和估值来源；用户一次确认后原子写回事实库，拒绝则事实库不变。
7. **逐经历选材**：对完整工作/项目经历池分别计算岗位匹配和简历组合价值。岗位匹配保留 70/55 等级；组合价值单独衡量板块补足、能力多样性、叙事独特性和同质化，不能与岗位匹配合并成不可解释的单一分数。
8. **写作前选材审计与检查点**：独立 Auditor 逐经历检查入选、落选和机会成本；用户确认事实映射、经历选择和真实缺口。事实仍不足时，由用户选择补充、诚实弱稿或跳过。
9. **双稿盲写**：只读 Writer 和只读 ASu Writer 并行生成结构化草稿，互不可见，只接收获批经历。
10. **草稿后基础质量审计**：启动全新的只读 Auditor，同时读取两份完成草稿、完整入选事实、JD 与要点预算；逐稿逐经历检查是否讲清对象/情境、个人动作、方法或决策、可背书结果与边界，检查是否存在一笔带过、事实有结果却未写、多个卖点挤成一句或简历腔异常。任一稿未通过不得进入融合。
11. **按要点融合**：协调器只在草稿质量审计通过后，依据事实支持、JD 价值和表达质量裁决，保留逐条决策记录，不得引入未获批经历。
12. **确定性与融合后审计**：先运行确定性规则，再由另一全新独立 Auditor 检查真实性、正向 JD 证据、选材质量、证据深度、HR 扫读和语言自然度；诚实缺口单独校验，不计作正向覆盖。
13. **独立 HR 决策审查**：基础审计通过后，由全新的只读 HR Reviewer 逐段判断是否足以推进面试；必须区分可用现有事实修复的表达问题和必须补问的事实缺口。
14. **重选、补问与修订**：选择/故事缺陷退回 Story Plan，单一 Writer 缺陷只重写该稿，融合/语言缺陷只重写 Fusion，事实冲突进入 `needs_input`。初稿加最多两次修复，共 3 个候选；仍失败则 `quality_failed`。
15. **内容批准**：草稿质量、确定性质量门、独立 Auditor、HR、调用回执和全部哈希同时通过后，只进入 `ready_for_user_review`；只有用户批准最终内容哈希，才写入当前版本指针。

## 6. 功能需求

### FR-01 调用与路由

- 支持 `$custom-resume <岗位目录 | JD文本 | JD URL>`。
- 支持“调用最新的简历 skill”“按 JD 定制简历内容”等隐式匹配。
- 支持 `ai_product_manager`、`game_production_pm`、`community_operations`、`community_product_manager` 和 `game_designer` 五个角色族。
- `community_operations` 必须选择 `community|content|growth|integrated`；`game_designer` 必须选择 `system|combat|writing|narrative|general`。其他角色族的 `role_track` 必须为空。
- 协调器可以根据 JD 提出角色与方向，但必须在参考研究和写作前由用户确认；方向不清时不得自行选择最容易包装的方向。
- HTML、模板、PDF 和视觉请求继续路由到 `/resume`，不得由本 Skill 隐式处理。

### FR-02 事实标识

- 经历具备稳定 `experience_id`，每条可用于简历的原子事实具备稳定 `fact_id`。
- ID 一经分配不得复用；事实文本变化不改变 ID，删除后 ID 保留为不可复用。
- 事实来源为 `observed` 或 `accepted_estimate`。

### FR-03 临时材料和候选补全

- 未确认内容不得直接写入事实库或干净稿。
- 候选补全可涉及过程、工具和结果。
- 对每段经历主动发散常见但未被事实确认的职责、分工、排期、校对、验收或复盘环节；这些内容只能作为 `candidate` 追问，确认前计分为 0 且不得进入干净稿。
- 估值区间经用户确认后可直接作为 `accepted_estimate` 写入事实库，并保留确认和口径信息。

### FR-04 证据映射与人工检查点

- 每项优先 JD 要求必须有证据等级和对应事实 ID。
- 写作前必须经过人工确认，不允许自动跳过该检查点。
- 只有确实无事实 ID 的要求才标记为无支持。

### FR-04A 能力迁移、参考与选材门禁

- 合格参考必须同时含内容样例、官方岗位来源和脱敏选择规则；不满足时进入 `awaiting_reference_approval`。
- 私有模范简历只在角色族完全一致、需要方向的岗位其 `role_track` 也完全一致，且 JD 关键词达到条目阈值时匹配；无匹配时不强行选择“最接近”样例。
- 模范简历内容及用途边界必须以哈希冻结；它可用于结构、证据分工、排序、要点预算和机会成本比较，但不得成为事实、分数、经历名单、要点或用户批准的来源，也不能单独替代独立参考研究门禁。
- 每段工作/项目经历必须先生成能力迁移链。链路包含 `fact_ids`、源动作、目标能力、目标要求、迁移距离、置信度和可写边界。
- 能力发散至少逐项检查八类能力：规划与项目推进、协作与利益相关方、质量与风险、用户与研究、数据与分析、内容与沟通、产品与技术、运营/商业与行业。未发现证据时明确记录无支持或候选问题，不能因为经历名称不典型而跳过检查。
- 迁移距离分为 `direct`、`adjacent`、`analogical` 和 `candidate`。前三者必须由事实蕴含；`candidate` 只触发追问。系统不得因发生场景不同而把近邻或类比能力直接归零。
- 岗位匹配仍按岗位职责、过程/交付、结果、行业、覆盖增量和证据强度分项评分，总分由代码复算；迁移证据按距离折算进入对应分项，不作为无上限附加分。
- 70+ 为核心；55–69 可作为辅助；低于 55 默认不得进入正文。只有行业亲和而无源动作证据时封顶 54；存在真实源动作的迁移证据不得被误判为 `affinity_only`。
- 每段经历另计算 0–20 的组合价值：板块补足、能力多样性、叙事独特性、非同质化各 0–5。组合价值不改变原始岗位匹配分和等级，但可影响最终选择与排序；选择低岗位分经历而排除高分经历时必须展示机会成本和理由。
- 写作前选材审计必须覆盖完整候选经历数，不能只审查已选内容。
- 同一定位的个人开发项目最多进入正文 2 项；系统必须按能力互补性选择，不得用多个相似 Agent/个人 Demo 重复证明同一能力。
- WORK/PROJECT 合计选择 1–4 段，不设最低 WORK 数量，不使用 `section_balance_override`。要点数只根据独立语义单元给出建议，不构成质量门槛；低于 55 分、无法形成完整证据叙事或没有行动加结果/影响证据的经历不得用于凑数。
- 经历属于工作还是实践必须依据已确认的合作/雇佣性质；不得为了满足板块数量自动把个人或社区项目改成工作经历。

### FR-04B 故事计划

- Writer 前必须生成 `story-plan.json`。每段入选经历包含 `story_thesis`、能力 ID、背景/行动/方法/困难/结果事实桶、一个或多个由证据语义决定的 `bullet_intents` 和内部 `ownership_guard`；intent 数量不作为质量门槛。
- 每个 intent 指定目的和所需事实；成稿每条 bullet 绑定 `experience_id`、`intent_id`、`fact_ids`，并在经历整体覆盖背景/问题、行动/方法、结果/影响。
- `ownership_guard` 只参与事实校验，禁止进入正文。无法支持完整故事时删除该经历、仅在同一真实经历内合并，或进入 `needs_input`。

### FR-05 独立写作

- Writer 与 ASu Writer 获得相同的批准输入包。
- 两个代理不接收对方草稿，也不能修改工作区文件。
- ASu Writer 使用项目内 ASu 方法，但仍服从事实和结构约束。

### FR-05A 角色专用证据边界

- 社区运营优先验证社群机制、用户沟通、活动执行、秩序维护、反馈闭环和社区健康度；内容运营优先验证选题、生产、编辑、分发和内容效果；增长运营优先验证漏斗、实验、渠道、转化、留存或召回。相邻方向可迁移，但不得因使用相同平台或指标而视为直接经历。
- 社区产品经理必须有事实支持的用户问题、需求分析、产品方案、交互/规则、协作推进或迭代验证证据；仅有社群维护、内容发布或活动执行时，只能作为运营侧用户洞察或近邻能力，不能写成产品 Owner。
- 系统策划优先验证规则、循环、资源、数值接口、配置和验证；战斗策划优先验证操作、技能、AI、关卡战斗体验、参数调试和战斗验证；文案策划优先验证世界观文本、角色/任务/系统文案、风格规范和编辑交付；叙事策划优先验证叙事结构、角色弧、任务链、分支、演出协同和玩家体验。综合策划只能整合已确认的多方向证据，不能用 `general` 绕过方向缺口。
- 游戏时长、测评、翻译、内容写作、MOD 测试或玩家反馈可形成行业、用户、质量、内容或近邻迁移证据，但不能单独证明系统设计、战斗设计、原创文案所有权或叙事系统设计。

### FR-06 融合与审计

- 融合以要点为单位，不整体平均或无依据拼接。
- 融合前必须存在与当前两份草稿哈希绑定且通过的 `draft-quality-audit.json`；Auditor 必须逐稿逐经历返回完整度、成果背书、信息密度和扫读质量结论。
- 任一 WORK/PROJECT 没有非空正文直接失败；空 bullet、机械拆句或换行不能冒充充实。各条必须覆盖不同 intent，不能以事实摘录冒充完整经历；要点数量本身不计分。
- 每条融合要点记录来源代理、事实 ID、取舍理由和是否重写。
- Auditor 独立执行真实性与 HR 质量审计。
- 第三个候选仍未通过则转 `quality_failed`，不得强制放行。
- 融合后机会成本审计可要求重新选材；协调器必须清空当前获批经历与草稿，返回人工选材门禁，不得自行换入落选经历。
- Auditor 通过后必须启动与 Writer、融合器和 Auditor 均隔离的 HR Reviewer；不得复用同一调用自证质量。
- HR Reviewer 逐段返回招聘 10 秒读感、JD 有效证据、具体缺陷、已确认但遗漏的高价值事实、面试影响、合理要点数和修订指令。
- HR 高标准通过条件为 `strong_push`、总分不低于 9.0、角色契合、叙事完整、证据具体、决策就绪、可信度和内容充实度六维均不低于 8.0，所有维度和经历判断引用最终 bullet 证据，并通过内容充实度硬指标：整稿不少于 1,200 个中文字符，核心经历正文不少于 180 个，辅助经历正文不少于 120 个；其他结果均不得进入用户审阅状态。要点数量不是硬指标。
- HR Reviewer 判断现有事实足够时进入定向修订；判断缺少事实时只生成问题；判断选材错误时回到选材批准。三种路径必须结构化记录。
- 每个入选 WORK/PROJECT 必须把该经历的全部已确认事实暴露给两名 Writer、Auditor 和 HR Reviewer；选材只能控制经历、迁移链和要点预算，不能先隐藏事实再让审稿器在不完整输入上给高分。
- Auditor 与 HR Reviewer 必须把成稿逐经历对照完整已确认事实集和故事计划；未使用的高价值方法、代表案例、质量控制、交付动作、决策或结果属于完成度风险，不能仅因正文真实、简短而自动通过。

### FR-07 内容结构与密度

- 顶层固定为教育经历、实习/工作经历、实践经历、自我能力。
- 教育经历按用户确认的固定基线原样输出，不按 JD 改写、重排课程或推导能力；当前基线仅保留汉语言文学课程，社会工作二学位只保留学校、专业和时间等已确认字段。
- Schema 1.5 新生成内容按角色族派生自我能力结构。`ai_product_manager` 使用“专业硬技能、综合软技能、个人优势”：非游戏岗位不生成游戏经历，CET-6 与真实翻译证据并入综合软技能，个人优势只从已确认的 Owner 意识、主动推进、依赖管理、问题闭环和结果负责证据中提炼。`game_production_pm` 和 `game_designer` 继续使用“专业硬技能、综合软技能、游戏经历、语言能力”；`community_operations` 和 `community_product_manager` 继续使用“专业硬技能、综合软技能、行业/平台经历、语言能力”。不得生成单句空栏目凑版面；历史不可变运行继续只读兼容旧结构与“游戏体验”旧名称。
- 游戏制作 PM 和游戏策划运行必须从本次冻结的最新事实快照重新选择自我能力内容；社区运营和社区产品经理也必须从当前事实重新选择行业/平台证据。旧简历、旧运行和聊天摘要不得成为事实或名单来源。事实摘要变化后必须重新分析，不允许只在旧文案上局部打补丁。
- 当 JD 要求丰富游戏产品经历且事实库存在具体产品证据时，“多品类深度玩家”等泛化标签不构成充分证据。游戏经历按目标公司/产品、准确描述的相近产品或长线形态、可核验深度、增加新品类/招聘信号的代表作依次判断；不得只按时长排序、把玩法差异明显的产品统称同品类、罗列库存，或把游玩外推为产品/商业化能力。
- 所有角色的语言能力优先表达已确认资质和可复用工作场景，不得仅复制已在项目经历出现的数量指标填充板块。
- 同时交付完整内容母版和一页信息密度稿。
- 内容母版以事实充分和模板适配为先，不再使用固定要点数或 1,500 字软上限驱动压缩。HR 内容门禁要求整稿不少于 1,200 个中文字符、核心经历正文不少于 180 个、辅助经历正文不少于 120 个；若已确认事实不足，应进入补问、重选或质量失败，不得机械拆句、同义反复或加入弱经历凑字数。
- 可使用由事实支持、层级一致的能力前置标签提升扫读；禁止把内部审计标签、验证备注或空泛标签写入正文。不能因“反标签”规则删除已有信息价值的能力标签。
- 选材与篇幅分配优先讲透最强核心经历；经历数量和要点数量本身都不构成质量。允许只保留一段强经历，但仍须满足整稿与逐经历的内容充实度门禁；事实不足时转补问或质量失败，不得保留同质、弱相关或无法展开的注水经历。
- “能力递进”只能重组事实已支持的能力层次或价值链，不能推导未经确认的时间顺序、成长因果或结果归因。
- “前三项高信号核心信息”指按最终正文阅读顺序最先出现、能够独立提供岗位正向证据的三项工作/项目经历标题或要点。

### FR-08 版本与状态

- 每次运行目录不可变；重新运行必须生成新的 `run_id`。
- 内容状态独立于岗位申请主状态。
- 已批准稿保存所引用事实的值摘要；仅引用事实变化时标记 `stale`。
- `run-status.jsonl` 追加记录批准、替代、用户拒绝、Schema 无效和撤销；阻断记录使旧批准失效。撤销当前稿后指针变为 `no_approved_content`，不自动回退。
- 用户明确批准后，可把通过真实性、基础质量和 HR 决策门禁的成稿登记为私有模范参考。登记时冻结 `role_family` 和条件性 `role_track`；登记不改变源运行的内容状态或申请状态，快照不可原地修改，更新时创建新 exemplar ID。

### FR-09 降级

- 子代理不可用时暂停，向用户提供重试或显式单 Agent 降级选择。
- 不得静默伪装盲写或独立审计已经发生。
- 联网研究失败时使用已有本地方法卡并标记研究降级，不影响事实边界。

## 7. 状态定义

`not_started → analyzing → needs_input/awaiting_reference_approval → awaiting_selection_approval → drafting → auditing → hr_reviewing → ready_for_user_review → approved`

`auditing → awaiting_selection_approval` 仅用于机会成本审计要求重新选材。

HR 缺陷按来源返回 Story Plan、单个 Writer 或 Fusion；事实冲突进入 `needs_input`；第三个候选仍不足时进入 `quality_failed`，不可批准。

- `failed`：输入、Schema、写入或代理执行发生不可恢复错误。
- `stale`：批准稿引用的事实值发生变化。
- 任何内容状态变化都不得自动推进现有申请主状态。

## 8. 明确不做

- 本轮不支持数值策划、关卡策划、任务策划、技术策划等额外游戏策划专用方向；不得把它们静默归入相近方向。
- 不为电商、品牌、公关、市场、用户运营等其他岗位族建设专用写作策略；只有 JD 被确认属于本版本五个角色族时才进入新版流程。
- 批量岗位编排；一次运行只处理一个 JD。
- HTML、PDF、模板选择、视觉验收或 ATS 页面验收。
- 网申填写、附件上传、消息发送或最终投递。
- 外部模型 API、常驻服务、数据库或复杂加密回执。
- 把未确认候选内容伪装为候选人的既有事实。

## 9. 验收标准

- 三种输入入口均能进入同一规范化流程。
- 事实 ID、差异确认、双稿隔离、融合、审计、版本和失效流程均有自动测试。
- 干净稿不存在无事实 ID 要点或未经确认候选。
- 每段候选经历均有能力迁移链；有事实支持的近邻/类比能力不会因经历标题不同而消失，潜在流程不会未经确认进入正文。
- 选材表同时展示岗位匹配分和组合价值；同类个人开发项目不超过 2 项，工作板块数量和任何板块平衡例外均可审计。
- 教育经历与固定基线逐字一致，自我能力分类符合约定。
- 角色族与方向组合由 Schema 1.5 确定性校验；社区/内容/增长运营、社区产品经理和五个游戏策划方向均有独立正向、缺口与方向混淆回归。
- 社区运营不会因内容产出自动获得增长实验所有权，社区产品不会因社群维护自动获得产品 Owner 身份；游戏经历不会因游玩、测评、翻译或测试自动获得策划所有权。
- 所有数字来自 `observed` 或 `accepted_estimate`。
- 结构、密度目标、审计报告和当前版本指针符合约定。
- Schema 1.5 运行必须包含故事计划、确定性质量门、`hr-review.json` 和匹配调用回执；基础审计高分但 HR 判断失败、HR 自报高分但缺回执、或没有用户内容哈希批准时均被阻止。Schema 1.0–1.4 历史运行保持只读兼容。
- HR Reviewer 能发现已确认高价值事实被压缩或遗漏，并把“可直接改写”和“必须补问”严格分开；按意见修订后需重新经过全部审计。
- 所有候选经历（包括未入选项）的事实输入必须与事实库对应经历的完整事实集合一致；预隐藏任一已确认事实是确定性失败，避免低估遗漏经历的机会成本。入选经历的同一完整事实集继续进入 Writer 与 HR。
- 完整稿通过证据叙事检查：强证据优先、核心经历完整、关键词有实际细节、每个强表述可由已确认事实支撑并经得住面试追问。
- 固定 5 个 AI PM JD 评测达到第 3.2 节门槛；游戏研发 PM 与 V1.5 新增角色/方向扩展案例通过相同真实性、五项质量和 HR 决策门槛。
