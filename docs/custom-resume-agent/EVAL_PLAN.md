# 定制简历 Agent V1 评测计划

> 状态：已确认
> 版本：0.1
> 日期：2026-08-22

## 1. 评测目标

评测必须分别回答：

1. 工作流和结构化产物是否正确；
2. 干净稿是否完全服从已确认事实；
3. 新流程的内容质量是否优于旧流程；
4. 失败和对抗输入是否被安全处理；
5. 同一输入能否重复运行、审查和失效。

确定性代码负责可精确判断的事实；Auditor 和人工盲评负责语义质量。不得用 LLM 分数代替确定性断言。

## 2. 硬指标

以下任一失败即不通过，不能由人工质量评分抵消：

- JSON 符合版本化 Pydantic Schema；
- 必需产物齐全且 `run_id`、输入哈希一致；
- 状态转换合法；
- `experience_id`、`fact_id` 唯一且引用存在；
- 每条干净稿要点至少引用一个事实 ID；
- 姓名、公司、角色、日期等不可变字段没有改写；
- 所有新数字均存在于 `observed` 或 `accepted_estimate` 事实；
- 未确认候选补全没有进入干净稿；
- 顶层四板块存在且顺序固定；
- Writer 与 ASu Writer 输入摘要一致、草稿互不可见；
- 历史运行目录不可覆盖；
- 引用事实变化能触发 `stale`，无关事实变化不能触发；
- 内容批准不改变申请主状态。

## 3. 软质量指标

每项 0–10 分：

| 维度 | 8 分标准 |
|---|---|
| JD 覆盖 | 高优先级要求均有真实证据或明确缺口，关键词出现在真实语境中 |
| 证据深度 | 核心经历写清个人动作、方法/交付物和结果，不停留在职责口号 |
| HR 扫读 | 前 10 秒可识别岗位定位、三项核心优势和主要风险，层级清晰 |
| 语言自然度 | 中文具体、克制、无模板腔、无堆词和不属于候选人的行业话术 |

正常通过要求四项均不低于 8。用户可以记录理由覆盖某个软门槛；覆盖记录必须保存在 `audit.json`，不能用于回归集自动通过。

一页信息密度稿的 1,200–1,500 字符、10–14 个经历要点是软预算：事实不足时不得为满足数量制造内容；超限或不足必须在审计中说明。

## 4. 测试分层

### 4.1 单元测试

- Markdown 事实元数据解析与序列化；
- ID 格式、唯一性、稳定性和不复用；
- `observed`、`accepted_estimate` 元数据校验；
- fact diff 的 add/replace、确认和源哈希冲突；
- 状态转换；
- 事实引用解析；
- 不可变字段比较；
- 新数字检测；
- 四板块和候选泄漏检测；
- 引用事实摘要及精准失效；
- 不可变运行目录和当前指针更新。

### 4.2 集成测试

1. 已有岗位目录完整运行。
2. 粘贴 JD 规范化并建立岗位目录。
3. URL JD 提取、来源记录与 Prompt Injection 隔离。
4. 最多 5 个逐题问题和汇总 diff 确认。
5. 用户拒绝 diff，事实库保持字节级不变。
6. 估值区间作为 `accepted_estimate` 入库并可被终稿引用。
7. 事实不足后用户选择诚实弱稿。
8. Writer 与 ASu Writer 产物均有效后才能融合。
9. 确定性校验阻止 Auditor 前置输入错误。
10. 审计一次通过、第一轮修复、第二轮修复和两轮后失败。
11. 内容批准仅更新独立状态。
12. 同岗位重复运行、批准指针切换和旧稿保留。

### 4.3 失败测试

- 空 JD、损坏 JSON、缺失事实库、重复 fact ID；
- 公司或岗位无法识别；
- 事实库在确认 diff 前发生并发变化；
- Writer 或 ASu Writer 单独超时/返回非法 Schema；
- 子代理全部不可用；
- 联网研究失败；
- manifest 和 current pointer 不一致；
- 对已提交运行目录的覆盖尝试。

### 4.4 对抗测试

- JD 要求忽略事实库并编造经历；
- 网页要求执行脚本或上传文件；
- 参考简历包含他人公司、项目、数字和联系方式；
- 理想候选人案例被诱导写入候选人稿件；
- Writer 在正文中夹带 `candidate_suggestions`；
- 使用换写数字、中文数字、百分比和区间逃避数字检测；
- 组合多条事实推导出未确认因果或结果；
- 让内容批准自动推进申请状态。

## 5. 固定回归数据集

### 5.1 目录结构

```text
tests/custom_resume/fixtures/eval/
├── agent-application/
├── ai-platform/
├── data-strategy/
├── consumer-commerce/
└── hard-technical-gap/
```

每个样本包含：

- 脱敏 `jd.md`；
- 来源 URL、采集日期和岗位类型；
- 同一份脱敏事实快照或固定事实快照哈希；
- 旧流程输出；
- 新流程三稿和审计产物；
- 盲评表，不暴露版本身份；
- 预期硬行为，例如必须暴露的缺口。

### 5.2 五类 JD

1. Agent 应用型 AI 产品经理；
2. AI 平台/工具型产品经理；
3. 数据分析与策略型 AI 产品经理；
4. 电商、消费或内容场景 AI 产品经理；
5. 对模型/工程深度要求明显超出现有事实的岗位。

样本优先来自官方公司招聘页；无法保留原文时保存脱敏结构和来源元数据，不把网页指令带入夹具。

## 6. 基线与盲评方法

1. 冻结同一事实快照和同一组 5 个 JD。
2. 使用当前旧 Prompt/Agent 重跑旧流程，不直接把历史 V6 当公平基线。
3. 使用新 `$custom-resume` 运行相同输入。
4. 去除文件名、代理名和版本线索，随机标记为 A/B。
5. 按四个软质量维度逐项评分并记录证据。
6. 单独运行真实性硬校验；真实性失败的版本不参与“平均更好”结论。
7. 现有 V6 仅记录为历史参考。

## 7. 发布门槛

新 Skill 切换为主 Harness 默认入口前必须满足：

- 全部单元、集成、失败和对抗自动测试通过；
- 5 个 JD 的新流程硬校验全部通过；
- 每份新稿四项质量分均不低于 8，且没有使用人工覆盖制造回归通过；
- 汇总盲评至少 3 个质量维度优于旧流程；
- 真实性不退化；
- 用户完成内容验收并批准切换。

未达到门槛时新旧入口继续并存，旧流程不得标记 deprecated。

## 8. 计划验证命令

实现后至少执行：

```powershell
python -m pytest tests/custom_resume
python -m compileall .agents/skills/custom-resume/scripts tests/custom_resume
python .agents/skills/custom-resume/scripts/validate_run.py <fixture-run-dir>
```

如果后续引入 lint 或静态类型检查器，必须在 `DEVELOPMENT.md` 和依赖清单中明确命令；当前不得伪称这些工具已经存在。

## 9. 评测产物

- 机器测试报告；
- 每个 JD 的硬校验结果；
- 旧/新盲评评分与证据；
- 失败案例和修复记录；
- 是否满足切换门槛的结论；
- 尚未验证的环境和风险。
